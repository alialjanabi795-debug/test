# Code RAG — Evidence Complementarity Pilot (الإصدار 0.1)

**الحالة:** هيكل تجربة وأدوات تحليل تعمل؛ **لا توجد نتائج فعلية على CodeRAG-Bench حتى الآن.**

## 1) هدف التجربة ببساطة

نختبر هل إضافة وثيقتين معاً تساعد نموذج توليد الكود على النجاح في اختبارات التنفيذ، حتى إذا لم تساعد كل وثيقة منفردة. ونقيس إن كانت سياسات اختيار الأدلة المعتادة تفوّت مثل هذه المجموعات، تحت ميزانية توكنات ثابتة.

**لن نتدرب نموذجاً جديداً أو DRL الآن.** يجب أولاً قياس حجم المشكلة على بيانات فعلية.

## 2) أساس العمل

- المصدر الرسمي: https://github.com/code-rag-bench/code-rag-bench
- الورقة المنشورة: https://aclanthology.org/2025.findings-naacl.176/
- DS-1000: https://github.com/xlang-ai/DS-1000
- مرجع مهم للمقارنة اللاحقة: PACE (2026), https://arxiv.org/abs/2608.25115
- **RepoEval-function يحتاج بيئة تنفيذ إضافية** في المستودع الرسمي؛ لا نفترض تشغيله بلا إعداد.
- بيئات DS-1000 قد تحتاج عزلاً للعمليات بسبب stateful test code؛ أي كود مولد ينبغي تشغيله في Sandbox/Container محدود الصلاحيات.

## 3) مراحل صغيرة

### مرحلة صفر: 5–10 مسائل (Smoke Test)

1. احصل على نسخة CodeRAG-Bench الرسمية وسجّل commit SHA والإصدارات.
2. تحقّق من إمكانية تشغيل حالة واحدة *بدون Retrieval* وتقييم الكود بمعيار المشروع الرسمي.
3. احصل على أفضل 5 أدلة لكل مسألة باسترجاع واحد **ثابت**. سجّل ID وطول كل وثيقة بالتوكن وترتيبها. لا تغير النص أو ترتيب الوثائق بين حالات المقارنة.
4. طبّع المدخلات إلى `candidates.jsonl` وفق التنسيق أدناه.
5. شغّل `prepare_manifest.py` لتوليد المجموعات الصالحة ضمن الميزانية.
6. عدّل adapter الخاص بعملية توليد/تقييم كود CodeRAG-Bench ليقرأ manifest، ويلتزم بالتوكنات والمحاذاة والتجارب المتكررة، ويكتب `results.jsonl`.
7. حلل الناتج بـ `analyze_pilot.py`.

### المرحلة التجريبية: 100–150 مسألة DS-1000/ODEX + 30–50 RepoEval-function

- المعايير: No Retrieval، جميع المفردات، جميع الأزواج الممكنة ضمن ميزانية 4096 توكن من خمسة مرشحين.
- اختيار خمس وثائق ينتج 1 + 5 + 10 = 16 حالة *قبل* استبعاد الأزواج التي تتجاوز الميزانية.
- استخدم 5 عينات توليد على الأقل لكل حالة عند القدرة، وبنفس قائمة البذور على جميع المجموعات.
- وثق النموذج والإصدار ودرجة الحرارة والـ prompt والـ tokenizer وميزانية السياق والـ max new tokens ومدة توليد كل عينة.
- إذا كنت تستخدم عينات غير حتمية، تكرار البذرة وحده لا يضمن التطابق عبر البيئات؛ سجّل الإعدادات ونسخة CUDA/المكتبة إن وجدت.
- لا تُدخل بيانات التقييم النهائي في التدريب أو اختيار hyperparameters.
- *لا تفترض أن وثائق Gold هي Oracle*. Oracle هنا يعني أفضل subset ضمن **مرشحين مختبرين بالفعل**، ويُستخدم للتحليل فقط.

## 4) الإدخال: `candidates.jsonl`

كل سطر كائن JSON لمسألة واحدة، بهذا المثال:

```json
{"task_id":"ds1000-123","dataset":"ds1000","group":"Pandas","docs":[{"id":"docA","rank":1,"tokens":290,"score":0.92},{"id":"docB","rank":2,"tokens":450,"score":0.78}]}
```

- `group`: اسم المكتبة في DS-1000/ODEX، أو المستودع في RepoEval؛ لتقييم التعميم لاحقاً.
- `rank`: ترتيب الاسترجاع يبدأ من 1.
- `tokens`: عدد توكنات الدليل *حسب tokenizer الخاص بالمولّد* بعد التنسيق النهائي المطبّق. لا تستخدم عدد الأحرف.
- عند حساب ميزانية 4096، يلزم أيضاً حجز overhead لعناوين/فواصل الوثائق والأوامر بحسب قالب الـ prompt الفعلي؛ قياس المجموع النهائي في adapter هو المرجع النهائي.

## 5) تشغيل أدوات إعداد المجموعات

```bash
python prepare_manifest.py --candidates candidates.jsonl --out manifest.jsonl --topn 5 --max-docs 2 --budget 4096
```

هذه العملية **لا تولّد كوداً ولا تشغّل نموذجاً ولا تنزّل بيانات**؛ تبني فقط جدول الحالات المطلوب اختبارها.

## 6) خرج وكيل التوليد: `results.jsonl`

مثال سطر حقيقي متوقع (قيمه توضيحية فقط):

```json
{"task_id":"ds1000-123","dataset":"ds1000","subset_key":"r1+r2","sample_id":0,"passed":false,"latency_s":3.12,"model_id":"<your-model-version>"}
```

- `passed`: Boolean صريح ناتج عن اختبارات benchmark الرسمية، وليس حكم LLM.
- `sample_id`: معرّف فريد للعينة، استخدم نفس لائحة الـIDs لكل مجموعة.
- `subset_key`: من manifest حرفياً (`none`, `r1`, `r2`, `r1+r2`, ...).
- **مهم:** يجب تنفيذ كود المولد في Sandbox محكم (عمليات، وقت، ذاكرة، شبكة، ملفات)، خارج آلة العمل الأساسية.

الـadapter المطلوب ليس مرفقاً لأنه يعتمد على بيئة الأجهزة والمولد ومسارات ملفات نتائج CodeRAG-Bench المحلية. يحدد `CODEX_IMPLEMENTATION_BRIEF.md` كيفية بنائه بأمان.

## 7) تحليل النتائج الحقيقية

```bash
python analyze_pilot.py --manifest manifest.jsonl --results results.jsonl --out real_report --min-samples 5
```

الخرج:

- `real_report/REPORT_AR.md`: ملخص عربي.
- `real_report/analysis.json`: المؤشرات على مستوى كل مسألة والمجموعات.

يشترط التحليل وجود جميع المجموعات المسموحة والحد الأدنى من العينات؛ المسائل الناقصة تُستبعد وتُذكر صراحة.

### المؤشرات التي ستحصل عليها

1. **Swing Rate:** نسبة المسائل التي تختلف نتائجها حسب الوثائق.
2. **Oracle Headroom:** الفرق بين أفضل مجموعة مجرّبة وTop-k. هذه فرصة متفائلة تم حسابها بعد رؤية النتائج، وليست أداءً قابلاً للنشر كسياسة.
3. **Complementary Pair Rate:** هل هناك زوج يحقق نجاحاً عالياً بينما كل عنصر وحده وخط الأساس لا ينجحان؟
4. **Positive Interaction Rate:** هل قيمة الزوج تتجاوز فائدة وثيقتيه منفردتين بعد طرح حالة دون مستندات؟
5. **Empirical Greedy Regret:** هل تفوّت طريقة اختيار تدريجية مبنية على نتائج الاختبار نفسها المجموعة الأفضل؟ **هذا تشخيص نظري باستخدام معلومات لا تتوفر وقت التشغيل وليس تطبيق PACE**. يجب لاحقاً تشغيل PACE الفعلي كـBaseline مستقل.

العتبات الاستكشافية الحالية (`0.2`,`0.8`) ليست برهاناً إحصائياً، و`5` تكرارات لا تكفي دائماً لإثبات وجود تأثير. قم بتقدير عدم اليقين وتأثير التكرار وترتيب الوثائق لاحقاً.

**محاذير:** الاختيار بأعلى نتائج مُقاسة على نفس البيانات يؤدي إلى optimistic selection bias؛ استخدمها لتقييم السقف المبدئي فقط. لا تقدمها كأداء Model قابل للنشر دون فصل اختبار نهائي.

## 8) اختبار هيكل الأدوات من دون نموذج (بيانات مصطنعة صريحة)

```bash
python test_pilot.py
python make_demo_data.py
python analyze_pilot.py --manifest examples/sample_manifest_SYNTHETIC.jsonl --results examples/sample_results_SYNTHETIC.jsonl --out examples/DEMO_ANALYSIS --allow-synthetic
```

البيانات مصطنعة لغرض اختبار عمل البرنامج فقط، والبرنامج يرفض تحليلها كأنها بيانات حقيقية إلا مع `--allow-synthetic`.

## 9) قرارات Phase 1

- إن لم تظهر Swing Problems أو فرصة تحسين فوق Top-k في الاختبارات الحقيقية: لا نبني خوارزمية تعلم.
- إن ظهرت أزواج تكاملية لكن Greedy قوي وPACE/مناظرها تختارها: لا ندّعي أن الفرضية تثبت قصور الطرق السابقة.
- إن ظهر Headroom ثابت عند أكثر من نموذج ومكتبة/مستودع: نفحص الإشراف بالـ execution مقابل likelihood **بنفس architecture** بعد عزل بيانات التقييم.
- لا تتوسع في DRL أو تدريب نماذج أو تغيير المجال قبل قراءة نتائج مرحلة القياس.
